# Local synthetic issuer records

The local Compose override adds a separate `DataProviderPlugin` to the pinned Certify 0.14.0 image. Upstream signing, authorization-token validation, holder proof validation and credential templates remain in Certify. The plugin is selected only when `INJI_LOCAL_DEVELOPMENT=true`; the base setup retains the upstream CSV provider.

`SyntheticFarmerDataProvider` takes the authenticated subject that Certify supplies after token validation. `SyntheticFarmerFactory` creates fictional farmer claims, visibly labelled `Synthetic Demo Farmer` and `DEMO-…`; it does not copy registration names, email addresses or any claimed real-world eligibility. `SyntheticFarmerDao` inserts one JSON record per subject in PostgreSQL using bound parameters and `ON CONFLICT DO NOTHING`, then returns the persisted record. Concurrent issuance and later sign-ins reuse the same row. Provisioning happens on first authorized issuance, not on registration alone.

The source is a local demo registry, not an authoritative agriculture database. A real issuer must replace this provider with an eligible-record lookup; self-registration must not automatically confer real entitlement. The plugin serves the three configured Farmer credential formats (JSON-LD, SD-JWT and mDoc) from the same record. Adding other credential types also requires corresponding issuer data, templates and verifier definitions.

Migration `006-synthetic-farmer-registry.sql` creates the table in `inji_certify`. Fresh seeds include it. For an existing local installation, run `npm run upgrade` while the stack is running. This migration is additive and preserves existing wallets and accounts. Keep `postgres-data` to retain the records. Deleting a Keycloak account does not automatically delete its issuer record or revoke already issued credentials; account/credential lifecycle management is outside this local demo.

## mDoc holder-key fix

The provider also serves `FarmerCredentialMdoc` (`mso_mdoc`, migration `009`), which Certify's own mDoc support builds and COSE-signs. Certify 0.14.0 derives the MSO device key from the holder DID by removing only the `did:jwk:` prefix. Inji Mobile's credential-offer proof names its key as `did:jwk:<key>#0`, so the `#0` fragment reaches the base64url decoder and issuance fails. Upstream fixed this on `develop` in [943185e](https://github.com/mosip/inji-certify/commit/943185e499), which no release contains yet (checked up to `v1.0.0-alpha.1`).

`patch/io/mosip/certify/utils/MDocProcessor.java` is [the pinned v0.14.0 source](https://github.com/mosip/inji-certify/blob/v0.14.0/certify-service/src/main/java/io/mosip/certify/utils/MDocProcessor.java), under MPL-2.0 (see `../../upstream/LICENSE`). Its only behaviour change is dropping the DID URL fragment before decoding, as upstream does. An explicit SLF4J logger replaces Lombok's generated logger so the class compiles with annotation processing disabled. The image compiles it against the image's own classes and replaces the class in `certify-service.jar`; the class is used only for `mso_mdoc`, so JSON-LD and SD-JWT issuance are unchanged. Remove the patch when adopting a Certify release that contains the fix.

The provider is compiled against the API and Spring libraries shipped in the pinned upstream image. `DataProviderPlugin.fetchData(Map)` and the original CSV provider were inspected from that image: the original CSV reader holds an in-memory map initialized from its file, which cannot serve newly registered subjects without a refresh. No upstream class is replaced.
